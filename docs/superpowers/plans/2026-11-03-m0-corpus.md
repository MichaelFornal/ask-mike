# M0: Corpus Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the raw material in `$ASK_PRIVATE_DIR/raw/` into a reviewed, gate-clean evidence corpus, `corpus/units.jsonl` plus `corpus/skills.json`, that Mike has approved unit by unit. Commit it to this public repo.

**Architecture:**
- Two kinds of extraction produce *proposed* units, stored privately in `$ASK_PRIVATE_DIR/work/`:
  - deterministic extractors read the structured sources: the profile's evidence items, roles, projects and education, plus the skill ledger.
  - a `claude -p` drafting step reads the prose sources and must quote each unit verbatim from its source.
- Every unit then passes five gates: privacy, slop, voice, honesty and numbers.
- Mike's rulings are applied.
- Mike approves, edits or rejects each unit in a generated markdown review sheet.
- An export step writes only approved, gate-clean units with public-safe source labels into the repo. A scanner blocks any commit that carries private patterns.

**Tech Stack:** Python 3.12 via uv, pytest. Runtime is stdlib only. `claude` CLI (`claude -p`, Max plan, $0).

**Spec:** `docs/superpowers/specs/2026-11-03-ask-mike-design.md`. The private version, `$ASK_PRIVATE_DIR/docs/design-private.md`, carries the don't-print specifics (§4), source paths (§6) and the M0 rulings list (§6, "Rulings Mike makes in M0"). Read both.

## Global Constraints

- **Public repo.** No phone, street, ZIP, personal email, salary, application or interview counts, applied-to company names, or don't-print terms in any tracked file, test fixture included. Fixtures use invented names ("Acme Robotics", "Widget Index").
- **Private data only through the environment.** Read raw material and write work files only under `$ASK_PRIVATE_DIR`, resolved by `askmike.private.private_dir()`. Never put absolute home-directory paths in tracked files.
- **No jb imports.** When a jb rule is needed, copy it with a `# copied from jb <file>:<line> on 2026-11-03` comment.
- **No API spend in M0.** Drafting uses `claude -p` only (`DRAFT_MODEL = "claude-opus-5-5"`).
- **Honesty ledger:** `none` is never claimed. `familiar` and `learning` are never asserted in a unit. `working` and `strong` are claimable.
- **Numbers:** every digit run in a unit's claim or detail is grounded in the unit's own source text or in a facts file's value/display. The only exemption is a 4-digit year from 1990 to 2030.
- **Voice:** third person; every claim contains "Mike". No first person (`I`, `my`, `me`, `we`, `our`). No em dash (U+2014) or en dash (U+2013).
- **Length:** claim at most 280 characters, detail at most 600.
- **Git:** commits use the repo-local noreply identity. Nothing is pushed.

## Review Focus

1. **A unit whose private source path or quote names a company Mike applied to.** It must never reach `corpus/units.jsonl`: export writes `public_source()`, drops `quote`, and gates claim/detail against applied-company names. Pinned in Task 9.
2. **Mike edits a claim in `review.md` and introduces an em dash, a `none` skill or an ungrounded number.** Export re-gates the edited text and refuses. Pinned in Task 9.
3. **The raw material is re-pulled after review and a unit's content changes.** Its earlier approval goes stale and returns to pending; it is not silently kept. Pinned in Task 8.
4. **`claude -p` returns malformed JSON, prose around the JSON, or a quote not found in the document.** Those units are dropped and counted, and the run continues. Pinned in Task 6.
5. **`review.md` is hand-edited badly** (a missing status line, an unknown id, a duplicated block, two boxes ticked). Parsing reports line-numbered errors and approves nothing from that block. Pinned in Task 8.

### Task 3: Loaders, the facts index and the deterministic extractors

**Files:**

**Interfaces:**
- Consumes: `Unit`, `SkillRef`, `Number` (Task 2)
- Produces:
  - `Skill(term: str, depth: str, aliases: tuple[str, ...])`, plus `load_ledger(raw: Path) -> list[Skill]`, read from `profile.json` `skill_depth`.
  - `class FactsIndex` with:
    - `load(raw: Path) -> FactsIndex`, reading three shapes: `site/facts.json` and meter-to-cash (`{"facts": {key: {"value", "display"}}}`), agent-census (`{"facts": {key: {"value"}}}`), deal-terms-desk (flat `{key: value}`)
    - `.match(token: str) -> list[str]`, returning `"fact:<file>:<key>"`
  - `number_forms(value) -> set[str]`: the forms one fact can match: plain, with thousands commas, and M/K abbreviations truncated (never rounded up) to 1–2 decimals. Example: 7,672,104 gives `7672104`, `7,672,104`, `7.67M`, `7.6M`.
  - `extract_evidence_units(profile: dict, ledger: list[Skill]) -> list[Unit]`: one unit per `roles[*].evidence[*]` and `projects[*].evidence[*]`.

    - claim is `"Mike " + claim[0].lower() + claim[1:]`
    - detail is the item's `bullet`, plus `metric` when the metric isn't already in the bullet
    - subject is the role's `company` or the project's `name`
    - kind is `role` or `project`
    - `when` comes from the parent's start/end
    - skills are `stack` terms mapped through ledger terms and aliases (case-insensitive); unmapped terms are dropped
    - origin is `extract`
  - `extract_fact_units(profile: dict, resume: dict) -> list[Unit]`: one `role-<slug>` unit per role ("Mike was <title> at <company>"; title and dates taken from the canonical resume `master.json` when it has the role, else from the profile) and one `edu-<slug>` unit per education entry.
  - `source_text(raw: Path, u: Unit) -> str`: the text a unit's numbers are grounded against. For extracted evidence that is the item's claim, bullet and metric; for drafted units it is the whole source document.

### Task 4: Gates

**Files:**
- Create: `askmike/gates/__init__.py`, `askmike/gates/patterns.py`, `askmike/gates/checks.py`
- Test: `tests/test_gates.py`

**Interfaces:**
- Consumes: `Unit` (Task 2); `Skill`, `FactsIndex`, `source_text` (Task 3)
- Produces:
  - `Finding(gate: str, unit_id: str, message: str)`. The message never echoes a matched private pattern; it names the pattern's index.
  - `GateContext(ledger: list[Skill], facts: FactsIndex, private_patterns: list[re.Pattern], source_text: Callable[[Unit], str])`
  - `load_private_patterns(private: Path) -> list[re.Pattern]`, built from three places:
    - `denylist.local.txt`
    - `dontprint.local.txt`
    - applied-company names derived at load time from `raw/jds/top50_index.json` `company` and the folder names in `raw/jds/applied/`. Strip the `-J1234` suffix and the `ats_*` prefixes; keep names of at least 3 characters as `\b<escaped>\b`.
      - These patterns match **case-sensitively**. Some company names are ordinary words, and case-insensitive matching flagged README lines on the first scan.
      - Identity and don't-print patterns stay case-insensitive.
  - Gate functions, each `(u: Unit, ctx: GateContext) -> list[Finding]`:
    - `privacy`: generic PHONE, STREET, and any email other than `mike@forn.al`, plus `ctx.private_patterns`, over claim, detail and quote.
    - `slop`: the `SLOP` list plus `HYPE = ["exceptional", "world-class", "passionate", "rockstar", "visionary", "ninja", "guru"]`, over claim and detail.
    - `voice`: first person, a claim without "Mike", or a length breach.
    - `honesty`: any ledger term or alias at `none`, `familiar` or `learning` that appears in claim or detail (word-bounded, case-insensitive), or appears in `u.skills`.
    - `numbers`: every digit token in claim and detail must be found in `ctx.source_text(u)` or by `ctx.facts.match`; years from 1990 to 2030 are exempt.
  - `run_gates(u: Unit, ctx: GateContext) -> list[Finding]`: runs all five gates in that order.
- **Copied rules:** `patterns.py` copies jb's `SLOP` (`raw/rules/build.py:2049`) and the `PHONE`/`STREET` regexes (`raw/rules/pf_gates.py:74-75`), each with a provenance comment. Before committing, check that none of the copied lines matches `load_private_patterns`.

### Task 8: The review sheet

**Files:**
- Create: `askmike/corpus/review.py`
- Test: `tests/test_review.py`

**Interfaces:**
- Consumes: `Unit`, `content_hash` (Task 2); `Finding` (Task 4); `near_dupes` (Task 7)
- Produces:
  - `Decision(status: str, claim: str, detail: str, hash: str)`. Status is one of `approve`, `reject` or `pending`.
  - `render_review(units, findings, dupes, decisions) -> str`. The sheet starts with a short "how to review" header, then lists units grouped by subject, ordered by gate findings first, then by origin. Each block looks like this:

```
## ev-widget-scale
- [ ] approve   - [ ] reject
claim: Mike built ...
detail: ...
subject: Widget Index · project · 2025-06..2025-09
skills: Python (strong)
numbers: 9 (text)
gates: OK            (or one "FAIL <gate>: <message>" line per finding)
similar: ev-widget-index
source: <private pointer>
```

  - `parse_review(text) -> tuple[dict[str, Decision], list[str]]`. It returns decisions plus errors such as `"line 41: block ev-x has no status line"`. Only `claim:` and `detail:` lines are editable. A block with an error yields no decision.
  - `merge_decisions(units, old: dict[str, Decision], new: dict[str, Decision]) -> dict[str, Decision]`:
    - a decision whose `hash` no longer matches the unit's current `content_hash` becomes `pending`
    - an edited claim or detail is kept as the override, with the hash of the unedited unit
  - CLI:
    - `review`: writes `work/review.md`, preserving earlier decisions
    - `ingest`: parses `review.md`, merges into `work/decisions.json`, prints approved/rejected/pending/error counts
